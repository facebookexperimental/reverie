# KVM same-process thread signal delivery

This change lets a supported `tkill` or `tgkill` send reach the named live thread in the same guest process. The existing backend returned `ENOSYS` for that sibling even when the target had an ordinary signal handler. It now publishes into the receiver's private pending queue and delivers at a supported receiver boundary. This is a separate prerequisite for the incomplete Hermit composition behind https://github.com/rrnewton/reverie/pull/538; no vector implementation or Hermit capability flag is included here.

The original composition at Hermit `7b9748c638deacfd9f3e13ba4640bf6ec38c92d2` and Reverie `8b0c5dbe01a52d888f8d9020ef5735fb3af41853` passed its strict descriptor matrix but failed the unchanged full guest after 100.812 seconds and the partial-signal guest after 100.703 seconds. The trace showed sibling `tgkill(3,3,10)` returning `ENOSYS`, followed by the receiver polling `preadv2`. The reduced pthread program passed native Linux and ptrace, while KVM returned pthread error 38 with zero deliveries. Those failures remain failures; this standalone change does not qualify that composition or enable its parked-write interruption flag.

## Ownership, lifecycle and lock order

`SharedThreadSignalState` contains the one authoritative blocked mask, alternate stack and private pending queue. A task's executor owns its strong reference. The lifecycle table stores a weak reference beside its existing task metadata; it cannot keep a retired task alive. Cloning the wrapper shares the same task state. The explicit fork, thread-clone and exec constructors still allocate separate state with their existing inheritance rules; a fork does not inherit a pending signal, and a thread does not borrow the parent's private queue.

A thread send holds the lifecycle lock from exact target/TGID validation through publication. It then takes the process-disposition lock and the receiver's signal-state lock, in that order. It checks the current receiver mask, runtime observation mode and disposition; it uses the current process disposition generation when enqueuing. Other signal consumers take process state before thread state, or take a single thread-state lock. No sender lock is held across a Tool callback, await, host I/O or signalfd readiness update. There is no secondary inbox and no later merge that could replace the first siginfo.

Retirement removes a registration only when its recorded generation still matches. Reusing a numeric TID clears the old weak reference, publishes the new queue, and cannot be undone by an old executor's destructor. Signal-zero probes validate task identity without queuing an event. A wrong TGID or absent target returns `ESRCH`; a live target outside the supported class returns `ENOSYS` before pending-state effects.

Successful leader exec performs fallible preparation and sibling teardown before the queue transition. It takes the lifecycle lock while copying the old pending state and installing the new endpoint, so a send accepted before the transition cannot be lost in an old queue after the snapshot. Failed exec leaves the old state and siblings intact. The existing process disposition generation invalidates signals predating an ignored disposition; a blocked signal accepted after that transition uses the new generation and survives a later handler installation. Fork copies process policy privately and starts with no inherited pending events.

These locks establish exact target ownership and a publication order; they are not a deterministic scheduler. Plain concurrent producers can still reach the lock in host-dependent order. Deterministic execution requires the external Tool scheduler to establish the causal send order before injection. This backend change does not alter Detcore's scheduler or selected turn.

## Receiver entry context

Existing syscall, signal-return and captured-fault boundaries continue using their current signal handling path. A new thread already has complete CPL3 registers before its first `KVM_RUN`, but has no consumed syscall frame to restore. The runtime therefore gives a signal selected after the child's Tool admission an explicit `ThreadEntrySignal` context and installs the handler registers directly. It does not synthesize a syscall or run the child's first instruction to create a boundary.

At this context, ordinary returning injections such as `gettid` work; fork, clone, exec, exit and other nonreturning process actions, plus tail injection, are refused before effects. Tool suppression resumes the original child continuation. An unblocked replacement enters its handler before that continuation; a blocked replacement is requeued in the same private queue and observed again only when it becomes eligible. Plain execution checks its initial pending state through the same frame-delivery helper, without claiming Tool admission for unmonitored threads.

The implementation does not interrupt arbitrary vCPU execution or wake arbitrary host-blocked receivers. Existing KVM `EINTR` handling is unchanged. Sibling `SIGKILL`, stopped-state scheduling, cross-process nonzero sends, ambiguous process-directed sends with live siblings, realtime queues and asynchronous `SIGCHLD`/`SIGPIPE` production remain unsupported. Existing threaded-signalfd refusal remains intact. No general asynchronous-signal or paired-backend determinism claim follows from enqueue success.

## Linux source and oracle accounting

Linux v6.17 `kernel/signal.c` uses `PIDTYPE_PID` for `do_send_specific` and selects the target's `pending` queue in `__send_signal_locked`. `legacy_queue` coalesces an already pending standard signal without replacing its first siginfo. An ignored blocked signal remains pending, whereas an unblocked ignored signal is discarded unless tracing requires a delivery stop. The previous suggestion that another thread could consume a thread-directed signal from a group queue was incorrect; the correction is retained at https://github.com/rrnewton/reverie/issues/317#issuecomment-5649945823. The issue remains open for its broader scope.

The native private-queue control queued payload 111, sent a duplicate `tgkill`, then queued payload 222. The sender had no pending bit and could not consume the receiver's signal; the receiver consumed payload 111 exactly once. All three native repetitions passed. Primary source: https://github.com/torvalds/linux/blob/v6.17/kernel/signal.c.

The first new live test had an incorrect libc oracle: it expected `SI_TKILL` from glibc `sigtimedwait`, and the native program failed with code 86 after returning signal 10 and `SI_USER`. Glibc deliberately converts `SI_TKILL` to `SI_USER` in that wrapper. The retained tests now have separate exact checks: libc must return `SI_USER`, and raw `rt_sigtimedwait` must return `SI_TKILL`. Handler and Tool siginfo checks remain exactly `SI_TKILL`; there is no widened accepted set. Primary source: https://github.com/bminor/glibc/blob/glibc-2.42/sysdeps/unix/sysv/linux/sigtimedwait.c.

The existing `leader_targeted_signal_does_not_mutate_worker_signal_state` retains its exact sender disposition, mask and pending-state assertions. Only its obsolete refusal expectation changes: success now additionally requires the exact receiver event and one dequeue. The existing ignored-self test explicitly selects Tool observation mode and retains its pending-event assertion. The old live signal-zero test also required a leader probe to fail. Its unchanged C source failed natively with exit 23 in 0.0019 seconds. The replacement retains the worker-versus-leader premise, both self probes and exact EINVAL requirement, and now requires native/plain/Tool agreement on live leader success, wrong TGID and absent TID ESRCH, plus unchanged masks and empty pending sets. This corrects a refusal requirement for newly supported behavior; it does not count enqueue success as receiver-delivery evidence. All other old functional oracles remain unchanged.

## Validation

Six new executor tests cover one-queue coalescing with complete first siginfo, wrong identities and effect-free unsupported sends, retirement/TID reuse, independent sender/receiver masks, plain versus Tool ignored handling, disposition generations and successful exec replacement. Existing fork-isolation and signal lifecycle tests remain present.

`sibling_signal_delivery_native_plain_and_tool` runs ten modes natively, through plain KVM, and through a real Tool: 30 guest executions. They cover worker-to-leader pthread delivery, leader-to-worker and sibling-to-sibling delivery, private blocked consumption and duplicate coalescing, delivery on unmask, ignored disposition transitions, failed exec, default process termination and exact libc/raw siginfo. Guest stdout and stderr are compared byte-for-byte; Tool admission, receiver identity, siginfo and callback counts are asserted.

`sibling_signal_before_first_instruction_with_tool` queues an event while the cloned child's start gate is closed. Four modes require delivery, suppression, replacement, or a blocked replacement deferred until unmasking. The first child memory observation precedes its first syscall. The Tool checks admission, exact receiver identity, returning injection and refusal of an injected fork before effects. The final ten-mode matrix and four entry modes passed together in 1.91 seconds (6.59 seconds including compilation). Earlier four-entry and nine-mode runs passed in 0.34 and 2.25 seconds respectively. Live tests require KVM when `REVERIE_REQUIRE_KVM=1` and use an outer 30-second process-tree deadline; native subprocesses have a separate five-second deadline, both with kill escalation.

The final `REVERIE_REQUIRE_KVM=1 cargo test -p reverie-kvm --all-features` run passed **605 tests, zero failures and zero ignored tests**, in 17.903 seconds including compilation (353 library, 238 static-ELF, and 14 other integration tests). Clippy with all targets/features and `-D warnings` passed in 3.809 seconds; formatting passed in 1.255 seconds. Removing entry delivery failed with guest exit 73 at the first memory observation in 0.12 seconds. Routing to the sender queue, replacing first siginfo, and removing a reused TID's endpoint from the stale destructor each made its exact focused test fail. Every temporary mutation was removed with byte-exact source restoration before final checks. The earlier failed runs remain separately retained. The initial full required-KVM parallel run had 352 lib passes and an existing initialization `waitpid(ECHILD)` failure; that case passed alone in 6.58 seconds. The first serial full run had 352 lib passes and an existing clear-child-tid test enrollment failure before guest execution (`FUTEX_CMP_REQUEUE` returned 0 instead of 1). Neither failure is converted into a pass or removed from the evidence.

## Review grounding

The review used the complete Reproducible Containers ASPLOS 2020 paper and appendix (DOI https://doi.org/10.1145/3373376.3378519), the complete Hermit scheduler at `7b9748c638deacfd9f3e13ba4640bf6ec38c92d2`, and the current parent product vision and roadmap. The paper's supported model does not itself establish guest-to-guest signal ordering; this extension requires explicit target ownership and causal scheduler delivery. The parent primary documents' capability definition remains the objective; dated backend limitations are not a lowered qualification threshold.

No gVisor source is copied. As in Linux and gVisor's thread/process pending separation, syscall routing, pending state and receiver delivery are separate responsibilities. This backend implements only the specified standard-signal subset, with explicit gaps above.

## Separate test synchronization and diagnostics

The initialization child originally published its nonleader host TID before `PTRACE_TRACEME`. Its parent immediately attempted `waitpid(TID, __WALL|WNOHANG)`, which can return `ECHILD` before the thread becomes a tracee. Delaying 30 ms between those exact operations made the original test fail with `ECHILD`; moving publication after successful `PTRACE_TRACEME` passed with the same delay and unchanged assertions and 15-second deadline. This establishes a source race, not the unrecorded historical interleaving. The retained original failed child's output contains only its test startup line; neither its configuration nor final status was persisted before cleanup.

The clear-child-tid failure occurred after the waiter had been requeued to a temporary word but before guest execution. Its exact waiter errno lived only in an unjoined thread result and was not retained on assertion failure. Diagnostics now capture that result through a channel before assertion unwinding; the exact expected requeue count and one-second futex deadline remain unchanged. A deliberate 1.1-second delay between the two requeues still fails and records `(-1, ETIMEDOUT)`. That validates the diagnostic and retains the failed deadline; it does not prove why the historical waiter left its queue. Four main baseline lib runs passed, so the historical failure's cause remains unresolved.
